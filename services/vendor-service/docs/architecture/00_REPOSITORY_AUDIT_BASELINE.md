## Cross-cutting conventions actually found (not assumed)

- **HMAC service auth**: `shared/go/serviceauth` (`X-Service-*` headers, HMAC-SHA256, `<PREFIX>_SERVICE_SECRETS=caller=secret,...` allowlist convention, confirmed identical across 8+ services). **No replay protection at the shared-package level** — the nonce is signed but never recorded as consumed. Only `fleet-partner-service` closes this gap locally (`internal/platform/noncestore`), by its own explicit design choice not to modify the shared package for every consumer at once.
- **Idempotency**: no shared package exists anywhere in the platform. Every service with real idempotency (fleet-partner-service, payment-wallet-service, hauling, dispatch) reimplements it locally with its own table and Go code. Vendor Service follows this same convention (`internal/platform/idempotency`) rather than inventing a shared dependency mid-architecture-phase.
- **Outbox/inbox/events**: four different tiers coexist — fleet-partner-service (Redis Streams, typed registry, consumer groups); payment-wallet-service/media-file-service (DB outbox + signed HTTP push, single fixed destination: Fleet); hauling/dispatch (feature-local outbox tables, hand-rolled HTTP push to Fleet); customer/taxi/notification/support-dispute/verification-compliance (no outbox — direct synchronous calls). No canonical shared implementation. Vendor Service's own `internal/events` follows the payment-wallet-service shape (the cleanest generic version per the audit) as a service-local package, with a `Publisher` interface left open for per-destination routing once real producers exist.
- **Migrations**: three different mechanisms — hauling's plain-numbered `.sql` + custom Go runner; dispatch's `.up/.down`-named files applied only by an external `psql` bootstrap script (no in-binary runner at all, and the service's own docs admit the files are "not all re-run-safe"); fleet-partner-service's/payment-wallet-service's own custom Go runner over `.up.sql`/`.down.sql` pairs with a query-driven (not hardcoded-count) rollback, avoiding a real bug class fleet-partner-service hit more than once. Vendor Service adopts the payment-wallet-service pattern exactly (`internal/database/migrate.go`), verified against real Postgres (apply → rollback → reapply, see [12_MIGRATION_OWNERSHIP.md](12_MIGRATION_OWNERSHIP.md)).
- **Workers**: dominant convention is a plain ticker + goroutine, registered directly in `cmd/main.go` (hauling's match-recovery worker, dispatch's push sender). Only `driver-dispatch-delivery-service` and `api-gateway` use a real task-queue library (`hibiken/asynq`), specifically for delayed/independently-retried single tasks. Vendor Service starts with the ticker convention (`internal/jobs`); asynq remains an option for a later fulfilment-planning section if delayed per-mission retries turn out to need it.
- **Feature flags**: `<PREFIX>_<FEATURE>_ENABLED` / `<PREFIX>_<FEATURE>_KILL_SWITCH`, confirmed across fleet-partner-service, hauling, dispatch, payment-wallet-service, media-file-service, verification-compliance-service. Vendor Service's flags (see [11_FEATURE_FLAG_AND_ROLLOUT_MODEL.md](11_FEATURE_FLAG_AND_ROLLOUT_MODEL.md)) follow the exact names specified in the implementation specification, which already match this convention.
- **OpenAPI / route-parity tests**: only fleet-partner-service has comprehensive, service-wide OpenAPI + contract-test packages. Dispatch and hauling each have exactly one narrow instance (their `private-execution` feature only). No other service has any. Vendor Service defers real OpenAPI until real routes exist (see [docs/architecture/](.) — no fake specs for unimplemented endpoints, per the task instruction).
- **`serviceapp.Run` bootstrap**: used by 10 of 13 services. `fleet-partner-service`, `driver-dispatch-delivery-service`, and `api-gateway` each roll their own `http.Server` for reasons specific to their scale/worker runtime. Vendor Service uses `serviceapp.Run` (the majority convention) — see `cmd/main.go`.

## Documented gap: local dev tooling referenced in CLAUDE.md does not exist in git

CLAUDE.md's "Local Development" section and its own Session Progress Log reference `infra/docker-compose.yml` and multiple `scripts/*bootstrap*.sh` files as if they exist and were committed. Neither the `infra/` directory, any `docker-compose*.yml` file, nor any `scripts/` bootstrap script exists anywhere in this repository's git history (`git log --all` over those paths returns nothing). Likewise, no service in the repository actually has a committed `.env.example`, despite CLAUDE.md's session log describing several being created. This appears to be prior-session work that was done in a local working tree and never committed, not fabrication — the application code itself (Go services, Flutter apps, migrations) is real and matches the documentation closely.

This was not "fixed" as part of this architecture task: recreating the entire platform's local-dev tooling is out of scope for a Vendor Service architecture foundation, and inventing a plausible-looking `infra/docker-compose.yml` covering 13 unrelated services would risk misrepresenting infrastructure that was never actually verified to work. Vendor Service's own `.env.example` was added (matching the documented-but-uncommitted convention, since it costs nothing and is genuinely useful), and this gap is disclosed here rather than silently worked around.

## No genuine architecture fork required a stop-and-ask decision

Every ambiguity the audit surfaced (migration engine, outbox durability tier, worker runtime, idempotency package location, whether to route through api-gateway) resolved cleanly to "follow the existing majority/most-mature convention" once evidenced — none of them were a case of the specification asking to reuse something structurally wrong for the new use case (the kind of fork that previously *did* warrant stopping to ask, on fleet-partner-service's private-execution work). Each decision and its reasoning is recorded in the relevant numbered document below rather than left implicit.
