# Section 30 — Database Migration and Backward Compatibility

## Scope

Three responsibilities, per the Section 30 mandate: (1) enforceable
database-migration safety rules; (2) a formal mapping of the original
single-service Fleet concept onto the current corporate architecture without
reintroducing deprecated ownership (see
`docs/section30-original-api-mapping.md`); (3) guaranteed backward
compatibility for independent-provider clients while adding
organization-managed provider capabilities. This document covers (1) and
(3); the mapping document covers (2).

This section does **not** redesign anything built in Sections 13–29. Every
historical migration (000001–000073) is treated as accepted baseline and was
not rewritten. The production changes are additive: migration replay and
inventory tooling, one internal membership-summary endpoint, optional
provider-login enrichment in the Dispatch and Hauling owner services, and
tolerant Flutter models. `PROVIDER_ORGANIZATION_MODE_ENABLED=false` preserves
the byte-for-byte version-1 independent-provider login response.

## 1. Migration safety principles

### 1.1 Additive-first

A migration in the current release must not immediately drop, rename,
narrow, or remove something still used by deployed code. Every one of this
repository's 73 migrations was audited (`internal/platform/migrationlint`)
and classified into one of nine categories:

| Category | Count (of 73) | Meaning |
|---|---|---|
| ADDITIVE | 19 | New table/column, no destructive shape |
| PERMISSION_SEED | 39 | Seeds `fleet_partner_permissions`/`fleet_partner_role_permissions` (almost every feature migration ships its own RBAC permission rows in the same file as its DDL) |
| ENUM_OR_STATE_EVOLUTION | 12 | Same-file DROP+ADD CONSTRAINT widening a CHECK-based state vocabulary |
| INDEX | 2 | Adds an index only |
| CONSTRAINT_EVOLUTION | 1 | `ALTER COLUMN ... SET NOT NULL` (migration 000045) |
| DESTRUCTIVE | 0 | — |
| DATA_REWRITE | 0 | — |
| BACKFILL | 0 | — |
| OPERATIONAL | 0 | — |

**Zero migrations in this repository's history classify DESTRUCTIVE.** Five
migrations (000056, 000057, 000059, 000061, 000063) initially appeared
destructive to a naive DROP-CONSTRAINT scan; inspection showed each is the
same safe idiom — discover an originally-unnamed inline CHECK constraint via
a `pg_constraint`/`pg_class` catalog lookup, then drop-and-replace it with a
wider, explicitly-named one in the same file (see `migrationlint.go`'s
`reDynamicCheckDiscovery`). This is exactly the "safe catalog lookup"
enum-widening pattern this section's own policy (1.3 below) requires; it is
not destructive.

The one CONSTRAINT_EVOLUTION migration (000045) combines `ADD COLUMN` +
an inline `UPDATE ... SET id = ...` backfill + `ALTER COLUMN ... SET NOT
NULL` in a single file, on `fleet_partner_organization_capabilities` — a
table whose cardinality is bounded by organization × capability count, not a
large operational table. This is accepted as historical baseline; a
`SECTION30-CLEANUP-RELEASE`-style backfill/DDL split (see 1.2) is the
required pattern for any *future* migration doing this on a table that could
be large.

### 1.2 Destructive-migration guard (for new migrations)

Because zero historical migrations are destructive, `CurrentTipVersion =
"000073"` is the accepted baseline in `migrationlint.go`. Any migration
numbered above it is held to the full new-migration policy:

- A migration classified DESTRUCTIVE must carry a `-- SECTION30-CLEANUP-RELEASE:
  <prerequisite release>` comment naming the release/version this cleanup
  depends on. `internal/section30contract`'s
  `TestPolicy_NewDestructiveMigrationRequiresCleanupMetadata` proves this is
  actually enforced (against a fabricated in-memory migration, since no real
  one exists yet) — not merely descriptive.
- `internal/section30contract`'s
  `TestInventory_NoUnexplainedDestructiveMigrationsInCurrentBaseline` re-runs
  the same check against the REAL, on-disk migration set on every `go test
  ./...`, so a destructive migration added later without the marker fails
  the build immediately.

### 1.3 Enum/check-constraint evolution

Prefer widening an existing CHECK constraint (drop the old one, add a wider
one, same file) over inventing a new lookup table when the state set is
small and rarely changes — this repository's own established convention
(12 migrations already do this). Two safe naming discovery idioms are both
accepted by `migrationlint`:

1. Static: the old constraint is named with a `_check` suffix or `chk_`
   prefix, dropped by literal name.
2. Dynamic: the old constraint is unnamed/autogenerated, discovered via
   `SELECT con.conname FROM pg_constraint con JOIN pg_class rel ON ... WHERE
   rel.relname = '<table>' AND pg_get_constraintdef(con.oid) ILIKE '%...%'`,
   then dropped via `EXECUTE ... || quote_ident(old_check)`.

`internal/section30contract`'s `TestPolicy_EnumEvolutionEntriesAreWideningNotNarrowing`
asserts every ENUM_OR_STATE_EVOLUTION-classified migration is structurally a
same-file widen, not a narrowing disguised as one.

**A new accepted state must be added to the CHECK constraint before any
application code emits it**, and an obsolete state removed only in a later,
explicitly-labelled cleanup release — never in the same migration that
widened it.

### 1.4 Up/down pairing and numbering

All 73 migrations have both an up and a down file; numbering is strictly
sequential 000001–000073 with no gaps or duplicates
(`internal/section30contract`'s `TestInventory_NumberingAndPairingIsClean`,
reusing `migrationlint.CheckPairingAndNumbering`). A migration whose down
would destroy legitimate data may declare
`-- SECTION30-NO-SAFE-DOWN: <rationale>` in its down file instead of faking
a fabricated reversible down;
`TestPolicy_NoSafeDownDeclarationIsHonoured` proves this exception path is
real (fabricated fixture, since no baseline migration currently declares the
marker). The generated inventory conservatively reports migration 000045 as
`rollbackSafe=false` and `dataLossPossible=true`: its down migration removes
the generated, backfilled capability identifier. It remains accepted
historical baseline, not a claim that operators may roll it down after new
data depends on that identifier.

## 2. Migration inventory — drift-proof by construction

`internal/platform/migrationlint.BuildInventory` computes the inventory
directly from the on-disk `migrations/` directory every time it runs —
there is no hand-maintained static list to silently drift the moment a new
migration lands. `internal/section30contract/TestInventory_CompletenessMatchesDirectory`
independently counts `*.up.sql` files via `os.ReadDir` (not reusing
`migrationlint.LoadMigrations` for the count side) and asserts the computed
inventory has exactly one entry per file.

Each `InventoryEntry` records: version, name, up/down file paths, category,
transactional flag (always `true` — see 4 below), tables/indexes/constraints
affected, rollback-safety, data-loss possibility, cleanup-release
requirement/note, and whether it is historical baseline.

Emit the inventory as JSON directly from the migration directory, with no
hand-maintained copy that can drift:

```bash
go run ./cmd/migration-inventory -dir ./migrations
```

## 3. Migration replay testing

`internal/section30contract/migration_replay_test.go` runs four tests
against real PostgreSQL (gated on `FLEET_PARTNER_TEST_DATABASE_URL`, skips
cleanly when unset — never runs against a database whose name doesn't
contain "test" or that looks like prod/staging/live):

| Test | WP8 sub-requirement | Result |
|---|---|---|
| `TestMigrationReplay_EmptySchemaAppliesCleanly` | (A) empty database, apply 000001→tip | PASS — verifies representative tables/columns/indexes from the earliest (000002) and latest (000073) migrations, and that the `organizations.status` CHECK constraint genuinely rejects an invalid value post-replay |
| `TestMigrationReplay_LatestMigrationRollbackAndReapply` | (B) rollback + reapply | PASS — rolls back 000073, verifies its columns/index are gone AND that 000055's table (a much earlier migration on the same table) survives, reapplies, verifies restored |
| `TestMigrationReplay_MultiStepRangeAcrossSections` | (C) multi-step replay | PASS — applies through 000054, verifies `fleet_partner_export_jobs` (created by 000055) does not exist yet, resumes to tip, verifies both its founding and later-added columns |
| `TestMigrationReplay_ExistingDataSurvivesUpgrade` | (D) existing-data upgrade | PASS — seeds a row right after `fleet_partner_organizations` is created (000002), applies every remaining migration including 000008's CHECK-widen, proves the row's original field values are unchanged |

### 3.1 Isolation strategy (and a fragility this found)

Each replay test runs against its own disposable **physical PostgreSQL
database** (`CREATE DATABASE`/`DROP DATABASE ... WITH (FORCE)` on the same
server as `FLEET_PARTNER_TEST_DATABASE_URL`), not merely a named schema. An
earlier version of this test suite used named-schema isolation instead, and
`TestMigrationReplay_EmptySchemaAppliesCleanly` failed with:

```
apply migration 000056_generic_imports: ERROR: constraint
"fleet_partner_bulk_imports_status_check_v2" of relation
"fleet_partner_bulk_imports" does not exist (SQLSTATE 42704)
```

Root cause: migrations 000056/57/59/61/63's dynamic constraint-discovery
query (2.3 above) filters only by `rel.relname = '<table>'`, with no
namespace/schema qualification. On the shared disposable test database
(which `internal/integration`'s own suite migrates into `public`), that
lookup matched `public`'s already-migrated row (already carrying the
widened `_v2` name from a prior test run) while the subsequent unqualified
`ALTER TABLE ... DROP CONSTRAINT` resolved, via `search_path`, to this
test's own separate schema — whose table still had the original,
differently-named constraint. Two different schemas' catalog rows, sharing
a table name, produced a name mismatch.

This is a **real fragility** in those five migrations' dynamic-discovery
pattern (a schema-qualified lookup, e.g. `con.conrelid =
'<table>'::regclass`, would be immune to it) — but it is a **test-only
artifact** for this repository today: every real deployment (Docker Compose,
every documented local bootstrap script) gives each service its own
dedicated database with only the default `public` schema, so the ambiguity
this exposed cannot occur in production. Per the mandate's explicit
instruction not to rewrite historical migrations to satisfy new tooling, the
fix was applied to the **test's isolation strategy** (physical database, not
schema) rather than to migrations 000056/57/59/61/63. The finding is
recorded here rather than silently worked around.

## 4. Backfill policy

This migration runner (`internal/database/migrate.go`) wraps **every**
migration file in its own `pool.Begin()`/`Commit()` transaction. A large data
backfill run inside that transaction would hold locks for the backfill's
entire duration — the exact anti-pattern WP9/WP10 warn against. This
repository does not do that: **zero migrations classify BACKFILL**
(`internal/section30contract/TestPolicy_NoBackfillClassifiedMigrationsInCurrentBaseline`
is a regression guard, not a tautology — it fails the moment one appears).

Large data population is delegated to the **Section 27 durable job
framework** (`internal/jobs`), already built and exercised throughout
Sections 27–29: bounded batches, `SKIP LOCKED` claiming, idempotency,
resumability via lease/heartbeat, progress tracking, failure classification,
dead-letter/replay, safe cancellation, metrics, and audit are all properties
of `fleet_partner_jobs`/`fleet_partner_job_attempts`, not something Section
30 needs to rebuild. No genuine current schema transition in this baseline
needs an actual new backfill job — inventing one solely to demonstrate the
pattern would violate the mandate's own "do not invent a meaningless
backfill solely to create a test" instruction. The pattern is: a migration
adds a nullable/defaulted column (schema only), a Section 27 job (using the
existing framework, not new infrastructure) performs the backfill in bounded
batches, and a later cleanup-release migration tightens the constraint once
the job confirms 100% coverage.

## 5. PostgreSQL version support

`internal/platform/pgversion`:

- `MinimumSupportedMajor = 13` — derived from evidence, not chosen
  arbitrarily: `gen_random_uuid()` is called directly (migrations 000045,
  000053) with **no** `CREATE EXTENSION pgcrypto` anywhere in the migration
  set. Before PostgreSQL 13, `gen_random_uuid()` only exists via the
  pgcrypto extension; PostgreSQL 13 made it a built-in. (Generated columns,
  migration 000053's `search_vector`, need only PostgreSQL 12+ — a lower
  bar than the `gen_random_uuid()` constraint.)
- `TestedMajor = 16` — this repository's actual development/CI PostgreSQL,
  confirmed live: `SHOW server_version` against the disposable test
  container (`karrygo-fleet-partner-test-db`, image `postgres:16-alpine`)
  returns `16.14`.
- `RequireSupported(ctx, pool)` queries the connected server and fails with
  an actionable message below the minimum. Wired into every
  `section30contract` migration replay test (`isolatedTestDatabase` calls it
  immediately after connecting), so a below-minimum test target fails fast
  with a clear message instead of an inscrutable mid-migration SQL error.
- `TestCheckMajorSupported_BelowMinimumFails`/`_AtOrAboveMinimumPasses` unit
  test the comparison logic directly; `TestRequireSupported_RealTestDatabaseMeetsMinimum`
  proves it against the real, live test database (major 16 ≥ minimum 13).

## 6. Index creation strategy

This runner's per-migration-transaction design makes `CREATE INDEX
CONCURRENTLY` categorically impossible inside any migration file —
PostgreSQL refuses it inside a transaction block, always, on every
environment. `internal/section30contract/TestPolicy_NoConcurrentIndexInsideAnyMigration`
scans every migration's up and down SQL and fails the build if the pattern
ever appears (currently: never does).

For a genuinely large live table needing a new index without a long lock,
the safe procedure is an **operator-run step outside the migration
runner**: `psql`/the deployment CLI issues `CREATE INDEX CONCURRENTLY`
directly against the target database, verified afterward
(`\d+ <table>` / `pg_stat_progress_create_index` / checking for `indisvalid
= false`, which marks a failed concurrent build and must be dropped and
retried — never left silently invalid). For a small or brand-new table
(true of every table this migration set has created so far), a plain
`CREATE INDEX` inside the normal migration transaction is safe and is what
every one of the two INDEX-classified migrations (000012, 000073) already
does.

## 7. Backward compatibility for independent providers

### 7.1 Boundary preserved

Independent providers are the pre-existing users of driver-hauling-service's
`truck_provider` app, driver-dispatch-delivery-service's `dispatch_provider`
app, and driver-taxi-service's provider surface — none of them have a row in
`fleet_partner_organization_provider_memberships` at all. Fleet-partner-service
never creates, modifies, or reads those apps' own auth/session/settlement
code paths; this section adds exactly one new file to those services'
consumption surface (the internal membership-summary endpoint, 7.3 below),
which they may call or ignore. Not calling it changes nothing about their
existing behavior.

### 7.2 providerMode

`internal/features/providers/models.ProviderMode{Independent,OrganizationManaged}`
are the two typed constants (`INDEPENDENT`/`ORGANIZATION_MANAGED`). There is
**no `MIXED` value** — `models.Membership.Live()`'s own doc comment
establishes a provider occupies at most one live membership per service
category (a single settlement slot), so simultaneous independent and
organization-managed standing within one category is not a state this
domain represents. Two hardcoded `"ORGANIZATION_MANAGED"` string literals
(`providers/repositories/providers.go`, `providers/usecases/provider_service.go`)
were replaced with the typed constant; a third hardcoded literal inside a
SQL `VALUES (...)` clause was replaced with a bind parameter (previously the
Go struct field and the SQL literal could theoretically diverge — they
cannot now).

Independence is represented by the **absence** of a membership row, never by
writing `INDEPENDENT` to a stored `Membership.ProviderMode` — there is no
membership row to write it on.

### 7.3 The membership-summary internal endpoint

`fleet-partner-service` issues no provider session itself — it owns no
provider identity or auth (README's "what it never owns"). WP19/20's
"login/session response gains providerMode" therefore cannot be implemented
as a change to a login endpoint this service does not have. Instead:

```
GET /internal/fleet-partner/v1/providers/:providerService/:providerId/membership-summary
```

An HMAC-authenticated internal read (mirrors the existing
`internal/features/backgroundops/http/internal.go` pattern exactly: caller
allowlist via `PROVIDER_MEMBERSHIP_ALLOWED_CALLERS`, defaulting to
`driver-dispatch-delivery-service,driver-taxi-service,driver-hauling-service`
— the same three services `FLEET_DOCUMENTS_PROVIDER_ALLOWED_CALLERS` already
trusts for an analogous provider-facing read). The owning Dispatch and Hauling
provider services call this server-side when
`PROVIDER_ORGANIZATION_MODE_ENABLED=true` and splice the result into login and
refresh responses they already own. A caller-supplied provider mode is never trusted — the
path only names WHICH provider to look up; `GetMembershipSummaryForProvider`
always derives the mode fresh from `FindLiveByProvider`'s authoritative
query (`status IN ('PENDING_PROVIDER_ACCEPTANCE','PENDING_SETUP','ACTIVE',
'SUSPENDED','ENDING')`).

Response shape (additive-only; every field beyond `providerMode` is omitted,
not null, for an `INDEPENDENT` provider):

```json
{
  "providerMode": "ORGANIZATION_MANAGED",
  "organization": {"id": "...", "displayName": "...", "status": "...",
                     "branch": {"id": "...", "name": "...", "type": "..."}},
  "membership": {"status": "...", "role": "...", "serviceCategory": "..."},
  "assignmentPolicy": {"assignmentMode": "OFFER", "providerDeclineRequired": true},
  "fieldVisibilityPolicy": "ORGANIZATION"
}
```

`organization` is built exclusively from `OrganizationReader`'s own narrow,
pre-vetted methods (`OrganizationStatus` → name/status only;
`BranchName` → name/type only) — never from the full `Organization`/`Branch`
models directly, so a field this summary was never given cannot leak by
accident. No customer contract price, company margin/commission, org wallet
balance/settlement value, internal finance/dispatcher note, or another
provider's data is ever in scope (WP25) —
`TestMembershipSummaryView_NoForbiddenFinancialOrCrossProviderFields`
enumerates every JSON field the response type (including nested types) can
ever emit via reflection and asserts none matches a forbidden-category
substring (`price`, `margin`, `commission`, `wallet`, `balance`,
`settlement`, `charge`, `fee`, `otherProvider`, `customerContract`).

`providerDeclineRequired` is always `true` — a platform invariant, enforced
by `fleet_partner_provider_policies`' own `UpsertPolicy` (hardcodes `true`
regardless of input) and its DB CHECK constraint, not merely a default.

### 7.5 Assignment/offer accept-decline compatibility

This was **not** rebuilt in Section 30 — it already exists and predates this
section: `internal/features/marketplace/http/internal_handlers.go` exposes
`GET /providers/:providerId/{offers,assignments,memberships}`;
`provider_response_handlers.go` exposes `POST
/assignments/:assignmentId/provider-{accept,decline,acknowledge}` and `POST
/marketplace-offers/:offerId/provider-{accept,decline}`. These routes
already carry the org-managed/independent distinction structurally (an
assignment always has a `MembershipID`; a marketplace offer does not),
which is the WP22 "safe discriminator" the mandate asks for — it was simply
already present, not invented here. Section 30's audit confirmed this
surface's existence and did not find a gap requiring new code.

### 7.6 Settlement compatibility

Payment-wallet-service remains authoritative for all settlement.
`internal/features/companywallet/http` exposes organization-facing wallet
routes and provider sub-wallet allocation/withdrawal routes
(`/providers/:membershipId/sub-wallet/*`) — these are for **organization-managed**
provider compensation only. An independent provider's own wallet/earnings
flow, owned entirely by their driver service + payment-wallet-service
directly, is never touched by any route in this package. Section 30 did not
find, and did not create, any code path that merges independent earnings
with an organization settlement projection.

## 8. Deprecation model

No route in this repository was removed or deprecated by Section 30 — every
change made is additive (7.2's constant fix is a refactor with an identical
runtime value; 7.3's endpoint is new). Should a future cleanup release need
to retire a compatibility route, the established convention (matching
`fleet_partner_organization_closure_*` and other lifecycle-tracked features)
is: a `deprecated` boolean and replacement-route reference in the response,
plus a `SECTION30-CLEANUP-RELEASE`-style comment/changelog entry naming the
approved sunset release — never removed while any evidenced client still
calls it, and never invented ahead of an actual approved sunset date.

## 9. Compatibility telemetry

Section 29's structured-logging/metrics discipline already forbids
user/provider/organization/request ID as a metric label (see
`docs/section29-reliability-observability.md` §1.3/§2); the new membership-summary
endpoint's request logging inherits that discipline automatically. The
`fleet_partner_provider_contract_responses_total` counter uses only bounded
`contract_version` (`1`) and `provider_mode` labels. Provider, organization,
membership and request IDs are never labels. No retained deprecated Fleet
endpoint or legacy field fallback exists, so corresponding counters are not
fabricated.

## 10. Operational runbook

### 10.1 Pre-deployment

1. `git status`/`git diff` review — confirm no unrelated file was touched.
2. Backup: follow `docs/section29-disaster-recovery.md`'s existing backup
   procedure — nothing about Section 30 changes it.
3. Migration inventory: run `go test ./internal/section30contract/...
   -run TestInventory` — confirms the 73-migration baseline (or a later
   count, if new migrations have landed) is numerically clean before
   deploying.
4. Pending migrations: none added by Section 30. A future release adding
   migrations should run `TestInventory_NoUnexplainedDestructiveMigrationsInCurrentBaseline`
   and `TestPolicy_NoConcurrentIndexInsideAnyMigration` as a pre-merge gate.
5. Lock impact: Section 30 adds no migrations, so there is none this
   release. A future migration should be classified via `migrationlint`
   first (ADDITIVE/INDEX are safe on any table size; CONSTRAINT_EVOLUTION
   or a large-table INDEX needs the 6-above procedure).

### 10.2 Deployment

1. Deploy the new binary — `go build ./...` is clean; no schema change ships
   with this release, so there is no ordering constraint between binary and
   schema for Section 30 specifically.
2. Keep `PROVIDER_ORGANIZATION_MODE_ENABLED=false` for the exact legacy login
   contract. Enable it independently in Dispatch/Hauling only with Fleet URL,
   caller and secret configured. `PROVIDER_MEMBERSHIP_ALLOWED_CALLERS`
   controls which signed owner services may call the Fleet endpoint.
3. Monitor: the endpoint's HTTP request logs (route
   `/internal/fleet-partner/v1/providers/:providerService/:providerId/membership-summary`)
   appear in the same structured log stream as every other internal route;
   watch for `403 caller_not_allowed` (allowlist misconfiguration) or `500`
   (an `OrganizationReader` failure — check `payment-wallet-service`/DB
   health, not this endpoint's own logic, since it has no independent
   failure mode beyond its two read calls).

### 10.3 Post-deployment

1. Confirm `go test ./... -count=1` is green (11 below).
2. If organization mode was enabled, confirm the owning service's
   login/session flow renders `providerMode` correctly for at least one known
   org-managed and one known independent provider in a staging environment
   before enabling broadly.

### 10.4 Incident procedure

- **Migration incident:** this release adds no migrations, so there is no
  migration-specific incident procedure to add. The general procedure
  (unchanged from Section 29): stop rollout, distinguish code-vs-schema
  rollback, never run a destructive `down` blindly against populated data,
  restore only from an evidenced backup, preserve outbox/audit/legal-hold
  state.
- **Membership-summary endpoint incident:** the endpoint is read-only and
  side-effect-free (it never writes). The safe immediate mitigation is
  unsetting `PROVIDER_MEMBERSHIP_ALLOWED_CALLERS` and redeploying/restarting
  — the route unmounts entirely (10.2.2), with zero effect on any other
  feature, migration state, or independent-provider behavior, since nothing
  else in the codebase depends on this endpoint existing.

## 12. Known, genuine gaps

- The five-migration dynamic-check-discovery fragility (§3.1) is real but
  test-only under this repository's actual deployment model; not fixed in
  migrations per the mandate's "do not rewrite historical migrations"
  instruction.
- `driver-taxi-service` is currently a capability scaffold rather than a
  production provider auth/session implementation, so there is no taxi login
  contract to enrich or fixture truthfully. Dispatch and Hauling — the two
  implemented provider auth owners — are wired and tested.
- No `v2` API version or content-type negotiation was introduced — none of
  Section 30's changes are incompatible with existing clients (all additive),
  so WP38's "only introduce a new version for a genuinely incompatible
  contract" bar was never met.
