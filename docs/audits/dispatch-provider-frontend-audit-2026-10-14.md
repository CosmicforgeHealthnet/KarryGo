# Dispatch provider frontend audit

Date: 14 October 2026. Scope: `apps/dispatch_provider`, `services/driver-dispatch-delivery-service`, relevant Wallet routes, and Vendor typography as a reference.

This is a source and contract audit. It does not certify deployed feature flags, external integrations, physical-phone layouts, or production readiness. No application/backend changes, builds, deployments or broad test runs were performed for this audit. References below are repository-relative.

## Assessment

The app has substantial integration already: OTP authentication and refresh, profile/onboarding, identity/licence/face uploads, vehicles, availability and GPS transmission, four request sources, legacy single-delivery execution, bank accounts/withdrawals, notifications, and support cases. These should be preserved and improved.

The frontend is not complete against the current backend. The largest gaps are operational mission execution and recovery. Several existing screens also misrepresent success, sample financial data, or missing data. Those issues take precedence over visual polish.

The backend contains customer, internal-service, admin and provider APIs. Only provider-authorized operations belong in this app. A route existing in source does not establish that its rollout flag is enabled on the VPS.

## UX direction

1. Use Vendor's Inter typography and teal action hierarchy, while keeping Dispatch's map and delivery workflow appropriate for riders.
2. Make Home show actual online/readiness/location state and the next meaningful task; expose approved own-provider totals only where allowed.
3. Keep map context and a collapsible task sheet during execution. Use a full screen for identity capture, complex proof, detailed history and multi-field account editing. Use sheets for short choices, filters and focused confirmations. Do not stack multiple sheets to complete one action.
4. Let the backend control the current stop, custody, allowed actions and review state. Explain blockers beside the affected action with a direct recovery route.
5. Distinguish success, submitted, pending, rejected, unavailable and unknown. A timeout after a mutation requires read-back/reconciliation, not an invented failure or success.
6. Prefer concise task-specific writing, meaningful icons, calm neutral surfaces, restrained illustrations for empty states and short purposeful transitions. No celebration before confirmation.

## Repair order and completion criteria

This is one fixed backlog; completed IDs stay completed. Implementation can group related IDs without adding new “remaining” items silently.

1. **Trust and state foundation:** D01, D02, D03, D05, D06, D13. Correct false success/data, isolate modes and fix error/recovery semantics.
2. **Shared design foundation:** D15, D16, D17, D18. Apply typography/tokens/components to active paths, including onboarding/auth.
3. **Home and activity:** D04, D11, D14. Real map/recenter, working pagination/filters and meaningful navigation.
4. **Operational parity:** D07, D08, D09, D10. Build existing backend-supported mission, handover and recovery flows with representative Mock scenarios and gated Live calls.
5. **Finance coverage:** D12 plus final application of D01/D03/D17. Confirm any missing provider history/analytics contract before extending the backend.
6. **Targeted final walkthrough:** fresh/returning/incomplete/suspended user; Mock and Live; no network/timeout/expired token; disabled rollout; pickup/delivery/recovery; dark/light; narrow phone, keyboard and large text. Reconcile uncertain writes and verify permission boundaries.

Completion requires truthful Live data and server-confirmed outcomes, no misleading active navigation, complete permitted rider actions, consistent reusable UI states, and phone verification. A successful analyzer run or attractive Mock dashboard alone would not establish completion.
